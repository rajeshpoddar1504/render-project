What is callable? How you execute Callable from ExecutorService?

Runnable interface's run method has return type void. so it cannot return any result from executing a task. However, a Callable interface's has a return type. If you have multiple return values possible from a task, we can use the Callable interface. Example:

 Callable r=()->{ Thread.sleep(3000); return "hello";};
        ExecutorService exe= Executors.newFixedThreadPool(2);
        Future<String> futureVal= exe.submit(r);
        System.out.println(futureVal.get());
        System.out.println("finished execution");
        exe.shutdown();

o/p: 	hello
	finished execution

futureVal.get() blocks the main thread from executing

ThreadPoolExecutor

It helps to create a customizable ThreadPool.

public ThreadPoolExecutor(int corePoolSize,
			int maxPoolSize,
			long keepAliveTime,
			TimeUnit unit,
			BlockingQueue<Runnable> workQueue,
			ThreadFactory threadFactory,
			RejectedExecutionHandler handler)

corePoolSize: number of threads are initially created and can be keep ideal in pool

allowCoreThreadTimeOut: if this property is set to TRUE (by default FALSE), ideal thread kept alive till time specified by 'keepAliveTime'.

keepAliveTime: Thread which get terminated after this time.

maxPoolSize-> max number of thread allowed in a pool
		if num of thread are ==corePoolSize and queue is also full then new thread is created till its less than 'maxPoolSize'.
Excess thread, will remain in pool, this pool is not shutdown or if allowCoreThreadTimeOut is set to true then excess thread get terminated after remain idle for KeepAliveTime

BlockingQueue: Que used to hold task, before they got picked by the worker thread. 
	Bounded Queue: Queue with Fixed Capacity
		like ArrayBlockingQueue
	Unbonded Queue: Queue with NO FIXED capacity
		like:LinkedBlockingQueue
ThreadFactory:
Factory for creating new thread. ThreadPoolExecutor use this to create new thread, this Factory provide us an interface to:
To give custom Thread name
TO give custom Thread prioity
TO set Thread Daemon flag etc

RejectedExecutedHandler:
Hander for tasks that cannot be accepted by thread pool.
Generally logging logic can be put here. For debugging purpose.
--new ThreadPoolExecutor.AbortPolicy -> throws RejectedExecutionException
--new ThreadPoolExecutor.callerRunsPolicy-> Executed the rejected task in the caller thread (thread that attempted to submit the task)
--new ThreadPoolExecutor.DiscardPolicy ->silently discard the rejected task
--new ThreadPoolExecutor.DiscardOldestPolicy -> discard the oldest task in the queue, to accommodate new task

why thread corePoolSize as 2, why not 10 or large value, what is logic behind?

Generally the ThreadPool min and max size depend on various factors like:
CPU Cores,
JVM Memory
Task Nature (CPU Intensibve or I/O Intensive)
Concurrency Requirement (want high or medium or low concurrency)
Memory Required to process a request
Throughput etc

if task is i/o intensive -> more number of threads
if task is CPU intensive -> less number of threads

and its an iterative process to update the min and max values based on monitoring
Formula:

max no of thread=no of CPU core*(1+request waiting time/processing time)

How to combine results of various thread executions?
By using completable future

Limitation of Future Class:
Say we wrote a method that retrieves data from a remote server, and chose to run it in a separate thread and return a Future.

1) Futures cannot be completed manually
if the remote service is down, we cannot complete a Future manually using the latest data available
2) Actions cannot be performed until the result is available 
Futures cannot perform further action until the result is avialble and it doesn't notify of its completion.
it provides a 'get' method which blocks until the result is avialble

3) Attaching a callback function is not possible
we don't have the ability to attach a callback function to the Future and have it called automatically when the Future's result is available
4) Multiple futures cannot be chained together
sometimes we'll need to execute a long-running task and when that task is done, we need to send its result to another long-running task and so on.

5) Multiple futures cannot be combined together
6) There is no Exception handling in Future API

for above limitation we have CompletableFuture
-------------------------
CompletableFuture implements the Future and the CompletionStage interfaces.
Provides a huge set of methods for creating, chaining and combining multiple Futures, it also have very comprehensive exception handling support.

thenApply vs thenCompose

if a callback function returns a Completable Future then use thenCompose

When to use which:
Use thenApply
when the next step in your asynchronous chain simply transforms the value of the previous CompletableFuture and does not involve another asynchronous operation that returns a CompletableFuture.
Use thenCompose
when the next step in your asynchronous chain involves another asynchronous operation that returns a CompletableFuture, and you want to avoid nested CompletableFuture instances, maintaining a flat chain of operations. This is common when you need to perform a subsequent asynchronous call based on the result of a previous one.

ex: 

CompletableFuture<CompletableFuture<String>> nestedFuture = CompletableFuture.supplyAsync(() -> "Hello")
            .thenApply(result -> CompletableFuture.supplyAsync(() -> result + " World"));

        nestedFuture.thenAccept(innerFuture -> innerFuture.thenAccept(System.out::println)); // Output: Hello World

        // `thenCompose` Example (Flattened CompletableFuture):
        CompletableFuture<String> flattenedFuture = CompletableFuture.supplyAsync(() -> "Hello")
            .thenCompose(result -> CompletableFuture.supplyAsync(() -> result + " World"));

        flattenedFuture.thenAccept(System.out::println); // Output: Hello World
